# AI Project Canvas: Predictive Maintenance

(เจ้าของ: คนที่ 8)

> ต้นทุนทางธุรกิจเป็นค่าสมมติ ส่วนตัวเลขผลโมเดลมาจากการรันบนข้อมูลจริง (Azure PdM) ดู [report.md](report.md)

| องค์ประกอบ | รายละเอียด |
|---|---|
| **Value proposition** | ฝ่ายซ่อมบำรุงรู้ล่วงหน้า 24 ชม. ว่าเครื่องไหนจะเสีย จึงเปลี่ยนการซ่อมฉุกเฉินเป็นการซ่อมตามแผน ลด downtime และค่าเสียหายจากสายการผลิตหยุด |
| **ผู้ใช้ / ผู้มีส่วนได้ส่วนเสีย** | ช่างซ่อมบำรุง (ใช้ผลทุกกะ), หัวหน้าฝ่ายผลิต (วางแผนกำลังผลิต), ฝ่ายจัดซื้ออะไหล่ |
| **งานของ ML** | Binary classification: `will_fail_24h` ต่อเครื่องต่อชั่วโมง |
| **ทำไมใช้ ML แทนกฎ** | อาการก่อนเสียเกิดจากหลายเซนเซอร์เปลี่ยนพร้อมกันและต่างกันตามชิ้นส่วน กฎ threshold เซนเซอร์เดียว (baseline) ได้ PR-AUC ต่ำกว่า XGBoost มาก (PR-AUC 0.088 เทียบกับ 0.999 บน validation) |
| **ข้อมูล** | Azure PdM: telemetry 876,100 แถว + errors 3,919 + maint 3,286 + failures 761 + machines 100 |
| **การแบ่งข้อมูล** | ตามเวลา: train ม.ค.–ส.ค. (193,400 แถว) / val ก.ย.–ต.ค. (48,800) / test พ.ย.–ธ.ค. 2015 (49,100) เพื่อกันการใช้ข้อมูลอนาคต |
| **Feature** | rolling mean/std 3 ชม. และ 24 ชม. ของ 4 เซนเซอร์, จำนวน error 5 ชนิดใน 24 ชม., จำนวนวันตั้งแต่ซ่อมแต่ละชิ้นส่วน, รุ่นเครื่อง, อายุ |
| **Optimizing metric** | PR-AUC (คลาสไม่สมดุล: positive 1.8–2.0%) |
| **Gating metric** | Recall ≥ 0.80, Precision ≥ 0.50, p95 latency < 100 ms, ขนาดโมเดล < 50 MB, PR-AUC ≥ champion |
| **ตัวชี้วัดธุรกิจ** | ค่าเสียหายรวม = FN × 50,000 + FP × 5,000 บาท, เงินที่ประหยัดได้เทียบกับไม่มีโมเดล, ชั่วโมง downtime ที่ลดได้ (threshold เลือกจากการลดค่าเสียหายนี้) |
| **ถ้าทำนายผิด** | FN: เครื่องเสียกะทันหัน สายการผลิตหยุด / FP: ส่งช่างไปตรวจโดยไม่จำเป็น เสียค่าแรงและเวลา |
| **การให้บริการ** | Real-time API (gateway ส่ง telemetry 24 ชม. ล่าสุด) + batch ทุกกะ จัดอันดับทั้งโรงงาน |
| **SLO** | p95 < 100 ms, error rate < 1%, availability ≥ 99% |
| **Drift ที่คาดว่าจะเกิด** | Data: เซนเซอร์เสื่อมหรือเปลี่ยนรุ่น, ฤดูกาล, สัดส่วนรุ่นเครื่องเปลี่ยน / Concept: วัสดุหรือชิ้นส่วนรุ่นใหม่มีรูปแบบการเสียใหม่, นโยบายการซ่อมเปลี่ยน |
| **Monitoring** | PSI ต่อ feature, live recall จาก `/feedback`, สัดส่วนการทำนายว่าเสีย, latency, error rate |
| **การเทรนใหม่** | เมื่อพบ data drift หรือ concept drift และทุกสัปดาห์ตามรอบ โดยต้องผ่าน gate เดิมก่อนขึ้นใช้งาน |
| **ผลบน test** | XGBoost: recall 0.997, precision 0.957, ต้นทุน 350,000 บาท เทียบกับ 44,700,000 บาทถ้าไม่มีโมเดล (2 เดือน, 100 เครื่อง) |
| **ความเสี่ยง** | ข้อมูลเป็นข้อมูลสังเคราะห์จาก Microsoft, label มาถึงช้า (รู้ผลจริงหลัง 24 ชม.), ต้นทุนเป็นค่าสมมติ |
