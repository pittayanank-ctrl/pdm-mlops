## ต้องเข้าใจ

**`ingest.py`**
- ดาวน์โหลด 5 ไฟล์ CSV จาก Azure blob ไปไว้ที่ `data/raw/` ถ้ามีไฟล์อยู่แล้วจะข้าม
- เขียนไฟล์ลง `.part` ก่อน แล้วค่อย rename เพื่อกันไฟล์ที่โหลดไม่ครบค้างอยู่
- `load_raw` แค่แปลงชนิดข้อมูล ยังไม่ตรวจความถูกต้อง เพราะการตรวจเป็นงานของ validation

**`sample_data.py`**
- สร้างข้อมูลสังเคราะห์ schema เดียวกับข้อมูลจริง ใช้ใน CI เพื่อไม่ต้องโหลด 80 MB ทุกครั้ง
- ก่อนเครื่องเสีย 36 ชม. เซนเซอร์ที่เกี่ยวกับชิ้นส่วนนั้นจะค่อยๆ เพี้ยน และมี error ถี่ขึ้น เพื่อให้มีสัญญาณที่โมเดลเรียนรู้ได้

**`labels.py`**
- `will_fail_24h = 1` เมื่อมี failure ในช่วง (t, t+24 ชม.] ของเครื่องเดียวกัน
- ใช้ `merge_asof` แบบ `direction="forward"` และ `by="machineID"` หา failure ครั้งถัดไป
- failure ที่เกิดตรงเวลา t พอดีไม่นับ เพราะเกิดไปแล้ว

**`split.py`**
- แบ่งตามเวลา ไม่สุ่ม: ถ้าสุ่ม แถวที่ห่างกัน 3 ชม. ของเครื่องเดียวกันจะตกอยู่คนละชุด โมเดลจึงได้ "เห็นอนาคต" (data leakage) แล้วได้คะแนนสูงเกินจริง
- `check_no_overlap` เช็กว่าแต่ละช่วงเวลาไม่ทับกัน

**`versioning.py`**
- เวอร์ชันข้อมูล = MD5 ของไฟล์ทั้งหมด ข้อมูลเหมือนเดิมได้เวอร์ชันเดิมเสมอ
- เวอร์ชันนี้ถูกบันทึกเป็น tag `data_version` ใน MLflow

## หลักฐานที่ต้องเก็บ

- ตารางจำนวนแถวและจำนวน positive ของ train/val/test (ดูได้จาก log ขั้น split ของ pipeline)
- `data_version` ที่เหมือนกันในการรัน 2 ครั้ง ซึ่งพิสูจน์ว่าทำซ้ำได้

## คำถามที่ต้องตอบได้

1. **ทำไมแบ่งตามเวลา?** กัน leakage และจำลองการใช้งานจริงที่เทรนด้วยอดีตแล้วทำนายอนาคต
2. **positive rate เท่าไร แล้วมีผลอะไร?** ประมาณ 2–5% คลาสไม่สมดุล จึงต้องใช้ PR-AUC และ class weight
3. **ทำไมเก็บข้อมูลทุก 3 ชม. แทนทุกชั่วโมง?** แถวที่ติดกันแทบเหมือนกัน (autocorrelation) จึงลดขนาดข้อมูลและลดน้ำหนักของแถวซ้ำๆ
4. **ข้อจำกัดของข้อมูลชุดนี้?** เป็นข้อมูลสังเคราะห์จาก Microsoft, มีแค่ 1 ปี, ไม่มีบริบทของโรงงานจริง
